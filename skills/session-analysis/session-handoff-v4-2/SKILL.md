# 接手

目的：让接手的人（常常就是你自己）几分钟内知道**现在真实是什么状态、第一步做什么**，然后开始干活。
地图说的是过去，现场说的是现在；两者对不上时以现场为准。建图和判断用强模型，规则同底座。

底座在本 skill 目录旁边的 `session-forensics-v4-2/`（和本 skill 同级，例如 `~/.claude/skills/` 或 `~/.agents/skills/` 下）：`export SESSION_FORENSICS_DIR=<本 skill 目录>/../session-forensics-v4-2`，`SF="$SESSION_FORENSICS_DIR/scripts"`；找不到就停下说明，不猜别的路径。

## 1. 先有地图

- 有 `<地图目录>/map.md`：读它。会话在地图之后还有新内容，按底座的更新模式并入（`ledger.py … --map <地图> --merge`）。
- 没有：按底座的流程自己建（`ledger.py … --skeleton` 起步；用户在另一个会话里让你接手的，加 `--origin`）。
  接手至少要填：请求归属、还开着和部分完成的请求、目标和确认状态、计划走到哪（`plan.now`）、主线、关键产物（`assets`，路径 + 是否还有效）。
- 跑 `inventory.py`：项目里现成的 skill、工作流、文档，原执行者用了哪些；接手的人照着用，不另起一套。

## 2. 核对现场

逐项做，结果写进 `site`（每项给 `id`，别处用 `site:<id>` 引用）：

| 查什么 | 怎么查 |
|---|---|
| 原执行者还在跑吗 | `python3 $SF/liveness.py <会话>`；在跑就**只读**，先问用户：停、等它收尾、还是分工 |
| 仓库状态 | `git status`、`git log --oneline -5`、未提交改动落在哪些文件 |
| 关键产物 | `assets` 里的路径逐个确认存在、最近修改时间；不对就改成 `stale` 或 `missing` |
| 进程和服务 | 地图提到的 dev server、后台任务、端口是否还在 |
| 说做完、没人核过的 | 「做到哪」只靠 agent 自述的，能核就核 |

## 3. 答案：接手型

`type: "handoff"`，必备项（底座的表）：

| 必备项 | 写什么 |
|---|---|
| 主线 | 由 `headline.alignment` 带出；当前那一步停在等用户拍板才是 `waiting` |
| 第一件事 | 一件具体动作 + 为什么是它 + 做完怎么验；同步写进 `headline.next` |
| 现场核对 | 一两句总结 `site`：哪些已核、哪些只是 agent 说的、谁还在跑 |
| 已失效 | 什么已经过时或被替代（产物、计划的一步、没人确认过的推断目标），没有就写「无」 |

`lead` 一到三句：现在的真实状态 + 第一件事。和接手直接相关、核过没补上的缺口写进 `answer.missing`。
给下一个人的精简地图就是 `render.py` 生成的 `map.md`。然后 `map_check.py --ledger … --verify --apply`、`render.py`。

## 4. 然后直接做

交付后立刻开始第一件事，除非：用户只要交接包；原执行者还在跑；这一步有副作用需要授权；第一件事就是等用户拍板。

## 规则

- 未完成和部分完成的请求逐条列出来。不说「需求已经足够」「基本完成」。
- 驱动工作的目标只是推断的，接手前问一句（带默认）：接手的人最容易沿着一个没人确认过的目标继续跑。
- 反问只问会改变第一件事的，带默认：没人答就按地图里排第一的下一步做。回复第一段就是 `answer.lead`，再给报告路径。
