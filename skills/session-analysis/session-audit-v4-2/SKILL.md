# 审计定责

目的：把「哪里不对」追到**一个具体机制**，找到**最早本该停下来的位置**。
对事不对人：用户的输入、agent 的判断、项目规范、工具，四处都可能是原因。建图和定责用强模型，核对者可以用 Sonnet 级。

底座在本 skill 目录旁边的 `session-forensics-v4-2/`（和本 skill 同级，例如 `~/.claude/skills/` 或 `~/.agents/skills/` 下）：`export SESSION_FORENSICS_DIR=<本 skill 目录>/../session-forensics-v4-2`，`SF="$SESSION_FORENSICS_DIR/scripts"`；找不到就停下说明，不猜别的路径。

## 1. 建图，请人核

- 主 agent 自己建一张地图（底座流程；用户在另一个会话里发起的，加 `--origin`，那里常写着定责的范围）。已有地图就读它，当材料。
- 请一位核对者：`brief.py challenger … --out <目录>/check`，核最关键的 5 条结论，回答「中心对不对」「缺了什么」。
  主因有两种说得通的说法时，加两次 `--rival "说法"`，让核对者顺带裁决；裁决主因就是定责，这时核对者也用最强模型。按证据裁决，不按票数。

## 2. 读项目规范和现成资源

- `inventory.py` 的清单里，和问题有关的 AGENTS.md、CLAUDE.md、项目 skill、工作流、hooks、检查脚本都读，**按执行当时的版本**（git log、修改时间、会话里注入的原文）。
- 对每条相关规范回答：当时加载了吗、遵守了吗、起作用了吗。现成的 skill 写着做法而这次没加载，本身常常就是主因链的一环。
- 审一个 skill 或流程：先用不含它术语的话复述它在帮谁、解决什么。「规范里没有 X」要从文件直读得出，用 `file:<路径>:<行>` 引用。

## 3. 答案：定责型

`type: "audit"`，必备项（底座的表）：

| 必备项 | 写什么 |
|---|---|
| 主因 | 一句话，停在一个能改的机制上（哪条输入缺了、哪个决策没确认、哪条规则缺失或没生效、哪个现成资源没用上、哪个工具读数失真）；同步写进问题的 `root`、`root_kind` |
| 主因链 | 从原因到后果按时间排 3–7 环，每环一句人话，位置放 `refs` |
| 本该在哪停 | 最早一个「在这里问一句或核一下，后面就不会发生」的位置和当时该问什么；只用当时可知的信息判断 |

`lead`：主因一句 + 本该在哪停一句。打转按问题定义：同一个问题连续 ≥3 次尝试、结果没稳定变好才标 `spin`，不算的写 `not_spin` 加理由。
有一行直接显示了机制才写 `root_basis: 物证`。证据链的细节可以另写 `ext` 块（`place: problems`）。

## 4. 要防再犯

用户要的是「以后怎么不再犯」时，答案用底座的 `process` 型（flows / table / watch）。定责这边只补两条：
- 改动表的「依据」指向问题和它出现的次数：同一种失败出现两次以上才值得改规范，只出现一次写进问题层就够。
- 主因和本该在哪停写进 `points`，让读者知道这些改动在防什么。改项目文件前先问用户。

## 5. 交付

`map_check.py --ledger … --verify --apply` → `render.py`。回复第一段就是 `answer.lead`，再给报告路径。
页面上不用「视角」「反方」「核对者」这类过程词；核对改掉了哪些结论，在「怎么查的」里用人话说明。
