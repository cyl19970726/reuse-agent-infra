# 目标与协作也要审

这是本项目调用 session-forensics 时的审计要求。原 skill 继续负责原始读取、测量和质证；本说明补充要检查的问题，不复制提取器，也不替代原 skill。session-to-workflow 将发现转成步骤、资产和评价方法。

## 一个判断：当时的输入能否支持当时的选择

用户原话证明其表达过什么，不自动证明技术事实正确、要求一致、信息充分或某种修法有效。用户也可以不知道全部需求；Agent 的工作包括识别哪些未知会改变路线、提出可比较的选择并维护已经确认的答案。

先恢复长期目的、当前阶段目标、本轮任务。三者是同一工作的目标上下文，不给“阶段→步骤→资产和流程”再加一层。检验每个重要动作如何服务最终目的，局部任务变化是否被误当成长期目标变化。

| 看到的情况 | 要核什么 | 如何归责与推进 |
|---|---|---|
| 请求缺少关键条件 | 当时上下文中是否已有答案；该未知会改变哪项取舍 | 确实缺失就说明输入缺口；Agent 应识别并澄清。不能仅据一个短句断言整个历史从未交代。 |
| 条件矛盾、事实错误或期待与资源冲突 | 原话、依据、当时可选方案和可预见后果 | 指出具体冲突及代价，请用户决定真实偏好；技术事实由 Agent 查证，不能让用户投票决定。 |
| 已说过却没有沿用 | 确认时点、后续派工/资产是否承接；是否有真实变更 | 归为上下文维护或执行遗漏，避免要求用户反复重述。 |
| 用户直接给出修法 | 先前的问题、Agent 是否独立诊断、修法如何改变结果 | 实际生产中可合理止损；评价自主性时记为用户提供的方法，不能记成 Agent 自主发现。 |
| 局部接受或后续修改 | 接受的是哪个版本、维度和范围；哪些要求继续有效 | Agent 负责记录和影响分析；不要从“图很好”推断事实、价格和发布均获接受。 |
| 作品修复与系统建设交替 | 本轮主要验证对象是否改变、方法改动是否真的改善产物 | 区分作品、工作流、工作台的成果；混合变更记录为比较限制。 |

每条重要发现写成：**输入/行为及出处 → 当时隐藏假设 → Agent 应识别的决策点 → 实际处理与后果 → 下次改变什么**。区分已观察、合理推断和未验证因果；没有时间数据就记真实纠正或返工事件，不编小时数，不把合法探索或生产止损说成用户错误。

## 追问的目标是更少返工

先读取并沿用已确认信息，给出对目标的简短理解。只问会改变执行路径、且不能从现有依据回答的未知，说明它影响什么。能独立推进的研究继续；影响昂贵制作的真实偏好保持待确认，不能把默认选项或沉默视为答案。没有必要每轮填写完整问卷。

研究前明确目的与必要边界，依赖研究内容才能判断的主题、载体和价格可在研究后定位。用户希望整套建议时，先还原历史，再把彼此影响的定位选择放在同一份方案里，供一次集中 review；不要拆成持续的零碎选择题。

## 两个 skill 的分工

- **session-forensics 的诊断任务**：核输入、理解、追问、决策、反馈及代价，指出用户和 Agent 各自可改善的具体行为；同样审计本轮审阅者有没有只核引文、漏核目标充分性。
- **session-to-workflow 的重建任务**：把以上证据用于 A1/相应目标步骤、研究后的定位资产、共享上下文和评价方案；不照搬每次用户给出的修法为必经步骤。

只读现行配置能证明目前有什么要求；断言历史没有某能力需要当时配置或执行证据。现有 forensics 已检查目标合同和目标变化，本项目扩展的是输入是否充分、双方如何形成决策、用户负担是否被掩盖。

## 评价结果和自主性要分开

同时观察产物质量与用户投入：提出问题、给出诊断、直接给修法、纠正同一要求、集中方向判断各有多少真实事件；时间只有实测才填。每个主要改进标触发来源：Agent 自主发现 / 用户指出问题 / 用户给出方法。澄清偏好不是能力失败，替用户完成诊断也不能归入自主完成。

检验“方法改善”时保持需求和输入可比；检验“补充目标是否有用”时把上下文变化作为单独变量。后来新增读者或价格要求不能只给新方法，再把全部改善归给 skill。先有质量，再看相近质量下用户能否少做诊断和催促；不能用不问问题换取低质量来声称更省心。

本轮发现只支持对应范围，审阅模板变完整不等于 Agent 已具备自主诊断能力。后续使用未参与改法提炼的案例，先不提示疑点，再观察它是否主动找出关键未知和协作代价。
