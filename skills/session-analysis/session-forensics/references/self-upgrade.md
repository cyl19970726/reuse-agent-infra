# 自我升级

## 为什么这一节必须存在

这个 skill 的每一次使用都会产出新知识：一条新签名、一个被推翻的阈值、一个解析 bug、一条够格晋升的
gate。**如果这些不写回文件，它们只存在于那一次会话的叙事流里，下次归零。**

那正是本 skill 用来诊断别人的病：**知识进了叙事流、没进物证流**。
不实现自我升级，这个 skill 就得了它自己诊断的病。

它也是晋升梯作用在自己身上的结果——skill 自身就是"复发 ≥3 次且有稳定操作序列"的产物。

## 分发层 vs 本地层（首次使用必读）

**基线、不满句式、洪水画像都是环境属性，不是通用常数。**
p50=10 次压缩、`view_image` 占 87% 输出——这些描述的是某一个人的语料。
换一个不用 subagent、不看图、说另一种语言的用户，分布完全不同。
拿别人的基线读自己的会话，**正是本 skill 要检测的 B 类裂缝：引用了一个在当前语境下不成立的东西。**

```
随 skill 分发（所有人相同）
  SKILL.md / references/*.md 的方法论部分 / scripts/*.py

本地校准产物（每人不同，绝不随 skill 分发）
  <skill>/local/
    baseline.json            本人语料的指标分位 + 本环境的工具输出画像
    dissat_candidates.jsonl  从本人历史挖出的不满句式候选（待人工确认）
    patterns.json            确认后的句式库
    gates.md                 本人项目的失效边
    falsified.md             本人推翻过的阈值
```

首次使用先跑校准：

```bash
python3 "$SESSION_FORENSICS_DIR/scripts/calibrate.py" \
  ~/.codex/sessions ~/.claude/projects
```

之后语料每增长一批就重跑一次。**指标只有相对本人基线的分位才有意义**——
绝对值（"failure_rate 0.33"）不可解释，分位（"你语料里的 p88"）才可解释。

⚠️ `references/signatures.md` 里出现的所有具体数字都带来源语料标注，
它们是**示例，不是常数**。读别人的 skill 文档时同理：先问"这个数字是谁的语料"。

## 每次使用后必答的五问

读完任何一个会话，在给出结论**之前**回答：

1. **出现新的洪水源 / 新签名了吗？** —— `flood_tool` 是否是表里没有的工具？是否有基线未覆盖的模式？
2. **有阈值被反例推翻吗？** —— 本次观测是否落在"应该命中却没命中"或"不该命中却命中"的位置？
3. **数字看起来不合理吗？** —— 不合理优先怀疑解析 bug，而不是怀疑会话。
   （实测教训：`patches=1370 / files=1066` 的怪比例，实际是正则吞掉了补丁体。）
4. **有东西跨会话复发第 2 次吗？** —— 是则晋升为 gate，不要等第 3 次。
5. **我上一轮发出的建议，造成了什么？** —— 仅适用于**连续审计**（同一对象多轮）。

### 第 5 问为什么必须存在（2026-08-11 实测，来源 `CASE-S`，代价：五支片带病交付）

审计员的建议**也是被审对象的输入**，因此**也在审计范围内**。不做这一步，
审计员就是这条链上**唯一一个不被审计的角色**——而这正是本 skill 用来诊断别人的 B 类裂缝
（引用了一个已不再成立/本就不完整的东西，且没有失效传播机制）长在自己身上。

实测经过：审计员连续两轮沿**单一维度**（token 成本）给建议，被审方照做，
做出 1200×1194 八拍合板 → **手只剩二三十像素** → 手部三种病全落盲区 →
五支片带病交付 → Owner 用三张放大截图打回。而可读下限那条规则**本来就写在
审计员自己引用的那一节里**，只是它只读了半段。详见 `local/gates.md` G20 边界。

⇒ 由此固化两条，与第 5 问一起执行：

```
单维度建议禁令   任何「减少 X」的建议必须同时写出「X 的下限由什么决定」，
                 否则该建议不完整、不得发出。
                 理由：只沿一个维度推，会把对象推到该维度的极值，
                 而极值处往往正是另一维度的失效点。
读完整节         引用自己的文档时必须读完该节全文。只读半段就下结论 =
                 「压缩致盲」在审计员自己身上的实例。
```

### 第 5 问的扩展（n=2 晋升，2026-08-12，来源 `CASE-S` 同一天两次）

审计员**两次犯下自己被授权去检测的错误类别**，两次都由被审方指出。这不是巧合，是结构：
SKILL.md §5 那张检查清单是拿来照别人的，没有任何机制把它照回自己身上。

```
第 1 次   把未核对的假设当前提提问
          「如果覆盖账其它 PASS 也是同一把带尺量的……」→ 整条建议建在这上面
          被审方一次 grep 核对：臂/手线不是带尺量的（特征直量/占据格体积/四机位目视），假
          ⇒ 命中清单里的「无证宣称」——前提也是宣称，也要标注待核

第 2 次   给一个不该承重的机制加固
          建议"给断崖检测器扩覆盖度 / 给 safe 戳标误差界"
          被审方把病根挪到上游：带读数是剪影空间陈述（永远为真），
          变成「裙甲忠实 0.96×」才中毒——毒在**归属**不在**检测**。
          正解是收窄检测器职能 + 命名行永远 registered，让没有特征宣称站在带值上
          ⇒ 命中清单里的「拿近似当判决」——在优化近似的精度，
             而没先问这个机制该不该承载这个判断
             （亦即 Owner 早已写下的 [[feedback-dont-refine-a-machine-judgment]]）
```

⇒ **发出任何建议前，把 SKILL.md §5 那张清单先照自己一遍。** 至少这两条：

1. **我这条建议里有没有未核对的前提？** 有则先核，或明确标为待核并**不要**把结论建在它上面。
2. **我是在给某个机制加固，还是在问它该不该承重？** 若建议的形状是"让 X 更准/更全/更细"，
   停一下问：**X 本来就不该承载这个判断吗？** 这条尤其容易在"帮忙优化"的语气下溜过去。

**由此确认的一类扫（被审方点名要求，已接受）**：`验证范围虚标` 是一个**类**，不是零散发现——
「目视锚定」（先读数后看图，两轨实为一轨）、「阳性对照当覆盖度」（只证灵敏度）、
「safe 戳含义超出实测」（"没有断崖型错配" ≠ "没有错配"）都是它的实例。
共同形状：**把"我验过了"的范围说得比实测大**。从下一轮起当固定扫描类目，不再逐个当新发现报。

#### 它的正面对应物：**对照强度分级**（`asserted` / `reviewable`），来源同会话，2026-08-12

「验证范围虚标」是事后被抓；它的**事前**形态是**在建对照的当下就标明它属于哪一级**。
被审方在采纳"把配准到的 z 也输出出来"这条时，主动记了效力边界（原话要点）：

> 摆出 z 使「找错特征」**可复核**（人看标点图），**不是机判**——机判需要独立于 localizer
> 的第二套特征定义，属过度工程。所以这个模式的对照强度是 **reviewable**，不是 **asserted**。

```
asserted     机判、可复算、可自动拒绝。例：band 21 阳性对照（抓不到已知答案即仪器错，自打回）
reviewable   人可核，但不自动。例：配准点标在曲线上，由人看它落没落在声称的特征上
（未标级）    默认会被下游当成 asserted 读 —— 这就是虚标的产生方式
```

⇒ 两条纪律：

1. **每个对照在建立时就标级**，写进它自己的输出/文档。不标级 = 默认被当成 asserted，
   而这正是「把"我验过了"说得比实测大」的产生机制——虚标往往不是有人夸大，
   是**没人写下界限，读的人自动补了个更强的**。
2. **reviewable 是合法档位，不是缺陷。** 硬要把它升成 asserted 常常是过度工程
   （此例：需要第二套独立特征定义）。正确做法是**承认它是 reviewable 并安排那次"人看"**，
   而不是假装它是 asserted，也不是因为够不到 asserted 就放弃这个对照。

#### 补：这块地板不是审计员专有的（同会话，被审方自陈）

被审方指出它自己在冠案里踩过同一块：**拿着 0.475× 直接优化"怎么修"（下变形令），
没先问"这个数有没有资格立案"**。加上审计员那两次，同一形状在同一会话里出现 **3 次、跨 2 个角色**：

```
沿用一个继承来的数/机制 → 直接在它下游优化 → 没有人问它有没有资格承重
```

⇒ 所以第 2 条自查（"我是在给机制加固，还是在问它该不该承重"）**不是审计员专属条款**，
它适用于任何接手一个既有读数/机制并准备在其上动作的角色。判据一句话：

> **在你为某个数/机制做任何下游动作之前，先说出它的立案依据。说不出就先别动它。**

## 纪律

- **每条新增必须带实测数字 + 来源会话 id。** 禁止"通常""可能""一般来说"。
  没有数字的观察写进"未证伪的假设"，不写进签名表。
- **只增不删已证伪条目。** 它们是防止重犯的唯一机制。删掉一条被推翻的阈值，
  三个月后一定会有人（包括你自己）重新提出它。
- **n=1 标记为「单例观察」，不得写成结论。** n≥2 才能晋升 gate。
- **心智模型层的改动需要 ≥2 个独立 case**，且必须说明它解释了旧模型解释不了的什么。
- **任何归一化 / 分类器的验收必须同时过 ≥2 个会话，且规模差 ≥100×。**
  实证（2026-07）：`top_shapes` 的命令归一化在 `CASE-F`（2.6 MB）上验收通过，
  接到 `CASE-A`（946 MB）上前 8 名有 5 条是 Codex JS 外壳——**只认 `cmd:"..."` 一种形态，
  漏掉 `{"cmd":"..."}`（键带引号）和 `tools.apply_patch(patch)` / `tools.write_stdin(...)`。**
  修好后两个会话前 8 名外壳噪声均为 0，并且 `js:apply_patch` 624× 让"用 exec 内嵌补丁"
  这条 gate 的违反次数**第一次变得可数**。单会话校准的归一化默认是过拟合的。
- **结论有边界就写边界，不要直接覆盖。**
  实例：早先"地板抬升不是杀手"在 18 次压缩下成立、60 次压缩下不成立 → 正确做法是补上适用区间
  （"~20 次内可忽略，>~40 次成为主要约束"），而不是把旧结论删掉。

## 对自己做审计（每次实质性修改后）

skill 自身也是会话产物，同一张签名表对它有效：

- **仪器分叉** —— 脚本是否在多处存在副本？
  实测已发生一次：`scratchpad/session_metrics.py`(307 行) 与
  `~/.claude/skills/session-forensics/scripts/session_metrics.py`(473 行) 并存，
  scratchpad 副本落后 166 行。处置：删除非权威副本，只保留 skill 目录下这一份。
  **草稿目录写脚本 → 稿件转正后必须删除草稿**，这是本 skill 自己的一条 gate。
- **定义分叉** —— 同一术语（如"探针/装配"、"A 类/B 类"）在 SKILL.md 与 references 中是否已漂移？
- **无证宣称** —— 文档里是否有没挂实测数字的断言？
- **上下文洪水** —— 单个 reference 文件是否大到每次加载都吃掉大量预算？超过约 200 行就该拆。

## 版本留痕

不维护版本号。**留痕靠「已证伪」表和「解析陷阱」表**——它们记录的是变化本身，
比版本号更有用：版本号只说"变了"，这两张表说"为什么变、变之前错在哪"。
